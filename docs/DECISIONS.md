부모는 같은 `host` 이고 자식보다 이전 시각인 `process` 기록에서 찾을 수 있었음.

**알게 된 것**

1. 다른 PC에 같은 pid가 21개 있음 (예: pid 24506은 WS-006과 WS-003). `host` 없이 부모를 찾으면 엉뚱한 PC의 프로세스가 섞이게 됨.

3. `rundll32.exe`는 `signed=True`임. 서명 여부만으로는 악성을 가를 수 없고, 명령줄(`MiniDump`)과 부모가 근거가 됨.
4. `cmd.exe`의 부모(`explorer.exe`)는 `parent_name`으로 이름은 알지만 생성 기록이 없음. 도구는 이 경우 `note`로 알려 줘야 함.

### text vs keyword (1일차)

<!-- 03 문서 1장의 질문에 대한 내 답과, 실제로 정한 매핑 -->

**질문:** 호스트 이름(`WS-007`)은 `text`와 `keyword` 중 무엇으로 저장해야 하나? 왜?

**답:** `keyword`. 호스트 이름은 쪼개서 찾을 말이 아니라 통째로 정확히 같은지 확인하는 값이다. `text`는 저장할 때 분석기가 소문자로 바꾸고 단어로 쪼개므로 `WS-007`이 `ws`, `007`로 나뉜다. 조사 도구는 `host`와 `pid`가 같은 기록을 찾는 것이라 `term` 조회가 정확히 맞아야 하고, 다른 PC가 섞이면 안 된다.

**직접 확인한 결과** (진짜 OpenSearch, 기록 3,161건)

| 쿼리                                     | 결과  | 알 수 있는 것                                  |
| ---------------------------------------- | ----- | ---------------------------------------------- |
| `host` term `WS-006`                     | 349건 | keyword는 통째로 일치                          |
| `host` term `ws-006` (소문자)            | 0건   | keyword는 대소문자도 구분                      |
| `cmdline`(text) match `MiniDump`         | 4건   | text는 단어 단위로 전문 검색                   |
| `cmdline`(text) term `MiniDump` (대문자) | 0건   | text는 소문자로 저장되어 대문자 term은 못 찾음 |
| `cmdline`(text) term `minidump` (소문자) | 4건   | 위와 같은 이유                                 |
| `cmdline.keyword` term `cmd.exe`         | 6건   | 명령줄 전체가 같을 때만 일치                   |
| `cmdline.keyword` term `MiniDump`        | 0건   | keyword는 부분 일치가 안 됨                    |

**정한 매핑**

| 칸                                                                | 타입                      | 이유                                                  |
| ----------------------------------------------------------------- | ------------------------- | ----------------------------------------------------- |
| `host`, `type`, `event_id`, `process.name`, `parent_name`, `user` | keyword                   | 정확히 일치로 거르는 값                               |
| `process.cmdline`, `script_text`                                  | text + keyword (`fields`) | 단어 검색(`MiniDump`)과 정확 일치·집계를 둘 다 하려고 |
| `ts`                                                              | date                      | 시간 범위(`range`) 검색                               |
| pid, ppid, 포트, 바이트                                           | long                      | 숫자 비교                                             |
| `network.dst_ip`                                                  | ip                        | IP 형식 검증과 대역 검색                              |

**포기한 것 / 주의**

- 명령줄을 text와 keyword로 둘 다 두면 색인 크기가 늘어난다. 대신 검색 방식이 두 가지가 된다.
- `ignore_above`(명령줄 4096, 스크립트 8191)를 넘는 값은 keyword로 색인되지 않아 정확 일치에서 빠진다(오류는 아님). text로는 계속 검색된다.
- `dynamic: strict`라서 매핑에 없는 칸이 오면 기록이 거절된다. 처음에 매핑이 비어 있을 때 25건이 모두 거절됐다. 새 칸이 생기면 템플릿을 먼저 고쳐야 한다.

### 01·09번 표 관계 복원 (D1-7 후 보정)

- `hi_res`도 비교했다. 01번은 `Table` 2개, 09번은 5개를 찾았으나 한국어 셀 내용과 헤더가 잘못 인식돼 승인권자 판단에 그대로 쓰기 어려웠다. 따라서 `fast`가 읽은 원본 글자와 PDF 표의 칸 좌표를 결합했다.
- `parse.py`는 01·09번의 `fast` 결과에서 표 안의 흩어진 텍스트를 제외하고, 각 행을 `Table` 요소로 다시 만든다. 09번은 자산 등급·조치·심각도·시간대를 승인권자와 한 행에 넣고, 연락표의 `〃`는 앞 행을 따르며, 다음 쪽 첫 행은 앞쪽의 심각도를 이어받는다. 3쪽의 선 없는 오탐률 표는 열 위치로 읽는다. ※1~3 설명은 해당 행에도 붙인다.
- `python -m soc.kb.ingest --dry-run --show 0`으로 **01번 요소 34개→청크 14개**, **09번 요소 103개→청크 92개**, **전체 120개 청크**를 확인했다. 01번 `호스트 네트워크 격리 → SOC 팀장`, `critical → 15분 이내`와 09번 평가 질문 k15~k21의 조건·답 7건을 각각 같은 표 청크 안에서 확인했다.
- 추가 패키지: 표 칸 좌표를 읽는 `pdfplumber>=0.11,<0.12`를 `requirements-kb.txt`에 추가했다. 실행 환경에서 `python -m pip install -r requirements-kb.txt`로 설치한다. 패키지가 없으면 `parse.py`가 설치 명령을 담은 오류를 낸다.
- 이 복원은 현재 제공된 01·09번 PDF의 배치에 맞춘다. PDF 판형·열 위치가 바뀌면 표 행과 승인권자를 다시 대조해야 한다. 05번 2단 읽기 순서, 06번 스캔 OCR, 07번 차트 수치는 이번 수정 대상이 아니다. Recall@3은 아래에 기록했으며 최종 답 정확도는 별도로 측정해야 한다.

### 첫 Recall@3 (1일차)

`kb-playbooks`는 단일 노드용 복제본 0개, 본문 `text`, 출처 `keyword`/쪽 번호 `integer`, 코사인 유사도 `knn_vector`로 설계했다. 표 HTML은 원본에 보존하되 검색 인덱스에는 넣지 않는다. 하이브리드는 키워드와 벡터 결과의 각 순위에 `1 / (60 + 순위)`를 더해 같은 청크 ID를 합친다. `search_playbook`은 계약대로 출처·쪽·종류·본문·RRF 원점수만 돌려준다.

2026-11-17 실측: 프로젝트 루트 PowerShell에서 `$env:PYTHONPATH='src'; .\.venv\Scripts\python.exe -m soc.kb.ingest`로 120개 청크를 적재하고 `.\.venv\Scripts\python.exe -m soc.eval.rag_eval --mode all`을 실행했다. OpenSearch 3.9.0 단일 노드, 실제 `text-embedding-3-small`(1536차원), `FAKE_LLM=false` 조건이다. 인덱스 건수 120개와 실제 매핑의 `cosinesimil`을 확인했다. `search_playbook("격리는 누가 승인해?", 3)`의 첫 결과는 01번 정책 PDF 1쪽이었다. 매핑, RRF 중복 처리·동점 순서, 도구 출력 형식도 로컬 코드 검사에서 통과했다.

하이브리드는 키워드와 벡터가 각각 놓친 k21과 k12를 보완해 18/21을 기록했다. k10은 06번 스캔 PDF에서 추출된 청크가 0개여서 세 방식 모두 실패했다. k13·k14의 한국어 질문 → 08번 영어 문서 검색도 세 방식 모두 실패했다. 표 복원 대상인 09번 문서 k15~k21은 하이브리드 기준 7/7이다. 이 Recall@3은 **정답 문서가 상위 3개 청크의 출처에 있는지**만 측정하며, 청크 안의 정답 문장 회수율이나 최종 답 정확도는 뜻하지 않는다.

### 가드레일 실패 처리 (2일차)

**구현한 검사:** G-1은 판정이 인용한 `event_id`가 조사 도구의 `seen_event_ids` 또는 알림의 `event_ids`에 없으면 `조회하지 않은 근거: <id>`를 반환한다. G-2는 `malicious` 판정에 서로 다른 근거 ID가 2개 미만이면 실패시킨다. 두 문제 목록은 `check()`가 합쳐 `ok`를 정한다.

**현재 실패 처리 방식:** 설정 기본값 `GUARDRAIL_ON_FAIL=retry`, `MAX_GUARDRAIL_RETRIES=1`에 따라 첫 실패에는 문제를 알려 주고 한 번 재조사한다. 재실패하면 허용되지 않은 ID를 제거하고 `malicious`를 `suspicious`로 낮추며 `needs_review=true`를 남긴다. 한 번의 재조사 기회로 추가 근거를 찾을 수 있게 하되, 계속된 재시도와 확인되지 않은 악성 판정의 리포트 유출을 막기 위해 횟수를 제한했다. 이 흐름은 기존 `nodes.py` 구현을 유지했으며 G-1·G-2는 `guardrail.py`에서 완성했다.

**검증 결과:** 구현 전 `tests/test_guardrail.py`는 4개 중 3개 실패했다. 구현 후 5개 모두 통과했고 `tests/test_graph_skeleton.py` 2개도 통과했다. 거짓말하는 `FakeLLM` 통합 테스트에서 `evt-fabricated-0001`이 최종 근거에서 제거됐고, 재조사 1회와 실패 로그 2건, 최종 `suspicious`·`needs_review=true`를 확인했다. `git diff --check`도 통과했다.

### 인프라 7단계 CI/CD 설계와 검증 (2026-11-19)
